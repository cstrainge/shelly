# Script REPLs with Reedline

Executable API for `std::terminal::readline`, 2026-10-13.

Expose the existing Reedline editor to Shelly scripts. Reedline continues to own editing,
undo, history navigation, menus, paste, terminal repainting and key interpretation. Shelly
owns application state and the read/evaluate/print loop. The standard module supplies a small
typed wrapper and ordinary stream adapters over private Rust primitives.

There is no evaluator inside this API. A database console, game console or API client can
interpret input however it wants. Entered Shelly source is also just text; evaluating it
requires a separate, explicit language API.

## Ordinary use

```shy
import std::terminal::{ readline }

let $editor = readline::Editor(prompt: "tools> ")
try
{
    for $line in $editor.lines
    {
        if $line == "quit" { break }
        echo "You entered: ${line}"
    }
}
finally { $editor.close }
```

`lines()` is a lazy `std::stream::Reader` of Strings. An empty submission is `""`, not EOF.
Ctrl+C discards the current draft and reprompts. Ctrl+D on an empty buffer ends the reader.
The loop body runs with ordinary terminal settings restored, so it can print, run commands
or make network requests. A break closes the borrowed stream, leaving the editor reusable.
The runnable [REPL example](../examples/repl.shy) demonstrates commands, completion, a dynamic
prompt and one application recovery boundary.

For applications with fallible commands, add one recovery boundary around each command:

```shy
for $line in $editor.lines
{
    if $line == "quit" { break }
    try { dispatch $line }
    catch ($stack, $error) { report_error $stack $error }
}
```

`dispatch` is the application's function. The editor neither catches evaluation errors nor
decides what they mean. Editor construction/read failures propagate to an outer recovery
boundary or the usual uncaught-error reporter.

## Editor surface

These signatures describe the implemented wrapper and its autogenerated constructors.
They use Shelly's existing syntax, function prototypes, conversion protocols and marked errors.

```shy
pub enum EditMode { Emacs, Vi }

pub fn Editor::new(
    $prompt: optional String | Prompt,
    $history: optional History,
    $complete: optional Complete,
    $validate: optional Validate,
    $highlight: optional Highlight,
    $edit_mode: optional EditMode,
    $limits: optional Limits
): Editor | Error

pub fn Editor::read($options: optional ReadOptions): optional String | Error
pub fn Editor::read_event($options: optional ReadOptions): ReadEvent | Error
pub fn Editor::lines($options: optional ReadOptions): std::stream::Reader | Error
pub fn Editor::remember($text: String): () | Error
pub fn Editor::flush_history(): () | Error
pub fn Editor::get_history_status(): HistoryStatus
pub fn Editor::get_draft(): String
pub fn Editor::close(): () | Error

pub fn read($prompt: optional String | Prompt): optional String | Error
```

`Editor` is an opaque shared handle. Copies are aliases, not separate editors. Its defaults
are prompt `"> "`, Emacs editing, isolated in-memory history, no application callbacks and
the existing Shelly manual multiline controls. It does not inherit the shell's history file,
completion symbols, prompt function or `$repl_*` settings. Color capability and `NO_COLOR`
are process/terminal properties and are respected.

The top-level `read` opens a temporary editor with history disabled, reads once with the
usual interrupt behavior, and closes it in finally. Repeated calls that should share history
use an Editor. There is no invisible singleton retaining input between scripts.

Prompt changes and prefilled input use `ReadOptions`:

```shy
pub struct ReadOptions
{
    pub prompt: optional String | Prompt,
    pub initial: optional String,
    pub cursor: optional Integer,
}
```

An omitted prompt inherits the editor prompt; `""` explicitly gives no prompt. An omitted
initial value starts with an empty buffer. Cursor defaults to the end of that buffer.
Both the initial buffer and cursor are validated before acquiring the terminal. Callbacks
are bound at construction and can read their application's captured state as it changes
between reads. Replacing whole callback configurations can be added later without requiring
it for ordinary REPLs.

## Input and control events

```shy
pub enum EventKind { Line, Interrupt, End }
pub struct ReadEvent
{
    pub kind: EventKind,
    pub text: String,
}
```

| Result | Meaning |
| --- | --- |
| `Line`, `text: ""` | A submitted empty buffer |
| `Line`, nonempty text | Exact submitted text, with embedded newlines preserved |
| `Interrupt`, text | Discarded draft; no submission or history record |
| `End`, `text: ""` | EOF; no submission or history record |

Submitted text excludes the key used to accept it. It is never trimmed or automatically
parsed. Native input/paste newline normalization remains Reedline's behavior; this is a
Unicode line editor, not an exact byte capture interface.

`read_event` exposes one of these events. `read` and `lines` consume Interrupt events and
reprompt. They return unit/stream EOF only for End. They consume the editing-time interrupt
exactly once; it must not also interrupt the next application command. An OS interrupt
during an active read has the same event behavior. An interrupt during the application loop
body uses Shelly's ordinary runtime interruption and cleanup behavior.

EOF makes the editor ended; later reads return End without reacquiring the terminal.
An explicit close instead makes the editor closed; reads then fail with ClosedError.
Close is idempotent. A terminal read failure ends that read, not the application: after a
catch the caller can retry when the terminal remains usable. A failed restoration marks the
editor unusable, and its subsequent reads fail.

The draft property is the most recent draft captured by cancellation or a failed read.
Successful submission and EOF clear it. Reads do not silently restore it: the caller can
explicitly pass `ReadOptions(initial: $editor.draft)`. Ctrl+C's draft is also carried in its
event. `read` intentionally discards that event and clears the draft when reprompting.

```shy
loop
{
    let $event = $editor.read_event
    match $event.kind
    {
        readline::EventKind::Line => { dispatch $event.text },
        readline::EventKind::Interrupt => { echo "Cancelled." },
        readline::EventKind::End => { break },
    }
}
```

`text` always has type String, so command handlers need no optional-value conversion.
The event kind distinguishes EOF from a submitted empty String.
The module does not print its own "Ctrl+C pressed" or "Exiting" messages.

## Prompts and styling

`Prompt` separates left text, optional right text and continuation text. The left text is
the entire primary prompt: the wrapper does not silently append `$` or a root marker.
The existing shell can still supply those markers in its own prompt adapter.

```shy
pub type PromptFn = fn(): String | Text

pub fn Prompt::new(
    $left: String | Text | PromptFn,
    $right: optional String | Text | PromptFn,
    $continuation: optional String | Text | PromptFn
): Prompt | Error

pub fn Prompt::from_string($text: String): Prompt | Error
pub fn Text::from_string($text: String): Text | Error
pub fn styled($text: String, $style: Style): Text | Error
```

Every part accepts plain text, styled Text or a zero-argument function returning either.
The module normalizes returned text with explicit Text conversion; this does not propose
general implicit conversion of function arguments. Applications can define their own
target-side conversion factories and call them explicitly. Callback function prototypes
describe successful values and still admit marked failures under Shelly's existing rules.

`Style` supplies optional foreground/background colors plus bold, dim and underline.
`Color` is a bounded native value constructed from an RGB triple, palette index, or a small
named color enum. Unspecified fields inherit terminal defaults. The adapter renders styles
according to terminal capabilities. Prompt and Text are immutable values, not terminal handles.

Prompt text is plain text unless styling is explicit. ESC, C0/C1 controls and unsupported
cursor/OSC sequences are rendered visibly rather than executed. Tabs and newlines in prompts
have documented layout meanings; carriage return is normalized to a line break. Raw ANSI
Strings are not an alternative style API. Completion labels and validation messages follow
the same display rules. The submitted source String remains separate and unchanged.

```shy
let $prompt = readline::Prompt(
    left: "database> ", right: "read only", continuation: "... ")
let $editor = readline::Editor(prompt: $prompt)
```

A dynamic prompt can bind functions directly:

```shy
let $database_name = "orders"
let $prompt = readline::Prompt(
    left: fn(): String { "database(${database_name})> " },
    right: "read only",
    continuation: "... ")
let $editor = readline::Editor(prompt: $prompt)
```

A named function reference such as `left: \`database_prompt` works too. Functions are stored
at construction and evaluated before each editing attempt, including a reprompt after Ctrl+C.
Evaluate each function part once, in left/right/continuation order, before entering raw mode;
literal parts need no invocation. The resulting prompt is immutable for that attempt.
Repaint, cursor movement and additional continuation lines reuse the cached values. A failure
in one part stops evaluation of later parts and propagates its concrete error and call stack
without entering editing mode or consuming terminal input.

Prompt functions execute as ordinary Shelly calls on the interpreter thread before acquiring
the editing lease. They may perform normal application work, including I/O, under the usual
runtime interruption rules. There is no implicit 50 ms editing-callback deadline for them.
The editor reserves its read before evaluating these functions, so recursively reading the
same editor fails BusyError rather than recursing. The adapter rechecks close/cancellation
and terminal ownership after evaluation. A prompt callback is not passed to a native painter
or worker thread. Applications should keep prompt preparation quick or cache expensive data.

Applications can also compute a prompt explicitly before a read:

```shy
let $line = $editor.read readline::ReadOptions(
    prompt: "database(${database_name})> ")
```

Both forms use the same prompt snapshot and display rules. Script prompt functions are never
invoked repeatedly by repainting or cursor movement.

Typed styling remains a small adapter: Color conversion factories accept an RGB `[Integer]`
of exactly three values in `0..255`, a palette Integer in `0..255`, or a NamedColor enum.
Style has optional `foreground`, `background`, `bold`, `dim` and `underline` fields. RGB and
palette inputs use explicit Color construction; booleans do not select colors. Text values
can be concatenated without flattening their style segments.

## Completion

```shy
pub type Complete = fn(Edit): [String | Completion]

pub fn words($values: [String]): Complete | Error
pub fn Completion::new(
    $value: String,
    $replace: optional Span,
    $display: optional String,
    $description: optional String,
    $append_space: optional Boolean
): Completion | Error
```

`Edit` is an immutable snapshot containing `text`, `cursor`, `revision`, `before_cursor`,
`after_cursor`, `word_span` and `word_prefix`. Cursor and all Spans use half-open UTF-8 byte
offsets, matching Reedline and Shelly source analysis. `Span.slice(text)` returns the exact
substring after checking bounds and UTF-8 boundaries. Shelly String indexing uses character
indices, so scripts must not use byte offsets directly as String indexes.

The default word is the maximal whitespace-delimited run containing the cursor. At a token's
end it is that token; after whitespace it is an empty insertion range. `word_prefix` is its
portion before the cursor. This is a raw-text convenience, without quote, escape or language
parsing. Domain completers can supply a different span, including the whole buffer.

Strings become completion values for that word span. `words` filters values by word_prefix,
preserves input order and removes duplicates. A custom callback's supplied results retain
its order and are not silently filtered or shell-escaped. Custom completions default to the
same span, display their value and do not append a space. Append-space only adds one ASCII
space when the next source character is not already whitespace.

All results in one request must replace the same span; that span must contain the cursor.
The entire result is checked before any insertion. Invalid ranges or mixed replacement spans
produce a callback contract error, rather than partially applying a suggestion. This makes
common-prefix completion deterministic. First Tab completes a unique result or extends its
common prefix; another Tab opens the existing menu. A custom completer owns escaping suitable
for its language. The generic module never assumes that the input is Shelly source.

```shy
let $editor = readline::Editor(
    prompt: "tools> ",
    complete: (readline::words ["help", "status", "quit"]))
```

Callbacks receive snapshots stamped with a revision. Native replies apply only to that exact
buffer/cursor revision. Native asynchronous completion providers can use Reedline's existing
pending/polling support behind this contract; the initial script callback API is synchronous
and bounded. There is no public future or background-task API implied here.

## Multiline validation and highlighting

```shy
pub enum ValidationKind { Ready, More, Reject }
pub struct Validation
{
    pub kind: ValidationKind,
    pub message: optional String,
    pub span: optional Span,
}
pub type Validate = fn(Edit): Validation
pub fn ready(): Validation
pub fn more(): Validation
pub fn reject($message: String, $span: optional Span): Validation | Error

pub struct HighlightSpan { pub span: Span, pub style: Style }
pub type Highlight = fn(Edit): [HighlightSpan]
```

Without validation, ordinary Enter submits. With validation, Ready submits, More inserts a
newline and Reject keeps the buffer with a feedback message. Reject is ordinary input feedback,
not a marked error. Callback bugs and runtime failures still propagate as errors.

The existing Shelly edit-mode adapter provides manual multiline entry: Ctrl+Enter enters
manual mode; Enter then inserts newlines; Ctrl+Enter again explicitly submits. Shift+Enter
always inserts a newline when supported. Explicit submission can override More, but cannot
override Reject. The wrapper runs the validation adapter on explicit submission too, even
though Reedline's Submit event can bypass its own completeness validator. Ctrl+C, EOF and
submission reset manual mode. On terminals without enhanced key reporting, More provides
portable automatic multiline entry.

Reedline's Validator trait has only complete/incomplete results. Reject is implemented by
the existing edit-mode adapter intercepting submission before handing it to Reedline; it
returns a repaint rather than an insertion. The message is displayed through Reedline's
native external-printer facility above the prompt, with any supplied span styled as feedback.
Enable the dependency feature needed for that facility. The wrapper does not build a separate
inline diagnostic renderer. Explicit submission passes through the same adapter.

Highlight spans refer to the original buffer. They are sorted, non-overlapping and within
UTF-8 boundaries; uncovered text gets the default style. Highlighting cannot replace source
characters. The adapter converts checked spans to Reedline StyledText. Its cache keys include
the buffer/cursor revision, so a cursor-sensitive callback cannot receive stale styling.
Callbacks may run again after movement or repaint; they must not depend on exactly-once calls.

```shy
# An application chooses this simple command-termination rule.
fn command_complete($edit: readline::Edit): readline::Validation
{
    if ($edit.text.trim).ends_with ";"
    { return readline::ready }
    readline::more
}

let $editor = readline::Editor(
    prompt: "query> ", validate: `command_complete)
```

This is an example application's rule, not a SQL parser. Shelly-aware completion/highlighting
can later be exposed as explicit native providers using the existing source-analysis snapshot.
The built-in shell keeps using its existing providers during the wrapper extraction; scripts
do not acquire interpreter evaluation authority merely by importing readline.

## Callback execution and errors

Complete, Validate and Highlight are success-only function prototypes. Functions that can
return marked failures fit them under Shelly's existing callback rules. The module's Error
union names its own failures; it is not a checked-exception list excluding application errors.

All script callbacks execute on the interpreter thread, under the authority captured when
the callback is bound. Completion, validation and highlighting can read captured state and
build values. During editing they
cannot write ancestor state, perform I/O, execute external commands, report errors, open a
nested editor or suspend in a native wait. The guard rejects those operations before they
take effect. This uses the same bounded, read-only execution mechanism as JSON metadata
providers; it does not attempt to infer purity from the callback signature.

Default budgets are 50 ms / 100,000 VM instructions per invocation, with bounded result
conversion. Completion is requested on Tab, not on every keystroke. Applications fetch slow
network/file data between reads and let the callback inspect cached results. Built-in native
providers can own bounded work outside script callbacks. These restrictions apply to editing
callbacks, not the application's loop body or prompt functions evaluated before editing.

An application callback's concrete marked error or runtime exception aborts the active read,
captures the draft, cancels pending callback work, restores the terminal, and then propagates
the original failure. It is not erased into a generic CallbackError. Invalid callback results
or exceeded callback budgets use the wrapper's CallbackError with the hook and reason.
No callback failure is printed while the terminal is in editing mode. Call stacks retain the
callback's script frames and the native boundary; bridge control packets refer to occurrences
kept on the interpreter thread. A terminal restoration failure is related Cleanup information
on the original failure, preserving both origins.

```shy
pub error struct TerminalError
{
    pub what: TerminalFailure,
    pub message: String,
    pub code: optional Integer,
}
pub enum TerminalFailure { NotTerminal, NotForeground, Read, Restore, Unsupported }
pub error struct ConfigError { pub message: String }
pub error struct BusyError { pub message: String }
pub error struct ClosedError { pub message: String }
pub error struct CancelledError { pub message: String }
pub error struct LimitError { pub message: String }
pub error struct CallbackError { pub hook: String, pub message: String }
pub error struct HistoryError { pub path: String, pub message: String, pub code: optional Integer }
pub type Error = TerminalError | ConfigError | BusyError | ClosedError | CancelledError | LimitError | CallbackError | HistoryError
```

As elsewhere, ordinary success consumption raises marked failures; explicit error-inclusive
bindings can capture them; catch matching preserves concrete identity; reporting uses the
prelude reporter and call stacks. EOF, Ctrl+C, validation Reject and empty completion lists
are normal outcomes requiring no error handling.

If an editing-time OS interrupt arrives while a script callback is running, native interrupt
control metadata cancels that callback and resolves the read as Interrupt after restoration.
An application-thrown payload merely saying "Interrupted" remains an application failure.
The distinction uses Shelly's occurrence control state, not an error message or type name.

## History

`History` is immutable configuration, not another lifetime to close:

```shy
pub enum HistoryRecord { Submitted, Manual }
pub enum HistoryFailure { Memory, Raise }
pub struct History
{
    pub path: optional String,
    pub limit: optional Integer,
    pub record: optional HistoryRecord,
    pub failure: optional HistoryFailure,
}
```

The default limit is 1,000 entries with a 16 MiB retained-text budget. An omitted path means
memory only. `History(limit: 0)` disables recording and history hints without filesystem I/O,
even if a path was supplied. Negative limits and invalid options fail before terminal entry.
Relative paths and `~` are resolved once at editor construction; later cwd changes do not
move the history file. Each Editor has its own session, even when configurations are reused.

Submitted mode records accepted nonblank text before returning it, including application
commands that later fail or are interrupted. Cancelled drafts, rejected input and consecutive
duplicate submissions are excluded. Multiline text is one record. Manual mode records only
`remember(text)`, letting applications omit secrets, normalize commands, or save only successful
commands. `remember` uses the same blank/deduplication/budget rules and never evaluates text.
Manual history cannot silently persist a submission through Reedline's built-in save path.

Persistent history reuses Shelly's existing JSON Lines format, stable sidecar locking,
session IDs, concurrent merge and atomic replacement. Private file permissions remain in
effect; a damaged file is preserved. Importing the module performs no history I/O. Initial
loading and merge occur at read boundaries outside editing; persistence happens after
terminal restoration. Disk work uses owned bounded native jobs, not script hooks.

With the default Memory failure policy, a disk failure retains usable memory history,
disables persistence for that editor, stores a normal diagnostic in `history_status`, and
reports one warning after restoring the terminal. It still returns the accepted input.
`HistoryStatus` exposes the active mode and optional non-error problem snapshot containing
path/message/code. There is no pending marked error buried in that snapshot.

Raise is explicit: a storage failure raises HistoryError and retains the accepted input in
`draft`, so the caller can recover it explicitly. `flush_history()` always reports failure
strictly; it does not silently claim durability. Close makes one best-effort flush under the
configured policy. History failures under Raise participate in normal finally cleanup error
relations. Job cancellation must preserve record IDs so a retry cannot duplicate an
already-committed record. Filesystem latency is not promised to obey a hard wall-clock bound.

```shy
let $editor = readline::Editor(
    prompt: "my-app> ",
    history: readline::History(path: "~/.my_app_history.jsonl"),
    complete: (readline::words ["help", "status", "quit"]))
```

The shell's `~/.shelly_history.jsonl` is used only if the script explicitly chooses it.

## Terminal ownership and pipelines

Each read acquires an exclusive process-wide editing lease for the foreground terminal.
Editor construction does not enter raw mode or reserve the terminal. Another Editor's read,
an alias read, or direct stdin consumption that conflicts with an active read fails BusyError
before consuming input. Check both stdin and Reedline's painting endpoint; with the current
dependency that endpoint is stderr. They must refer to the same foreground terminal.
Redirected stdout is allowed. If stdin/stderr is not suitable, return TerminalError rather
than secretly opening `/dev/tty` or switching to a different parsing interface.

Prompts, menus and editor messages go through Reedline's painter. The wrapper does not print
them into data pipelines. Cursor-shape configuration that makes Reedline's destructor emit
stdout escape sequences remains disabled. Plain nonterminal input uses `std::io` readers
and line adapters explicitly. The existing `open_terminal`/Terminal API controls a child PTY;
it is a separate capability and is not implicitly used as this editor's input device.

`lines()` borrows an Editor and uses the existing stream's whole-consumer lease. Acquisition
is exclusive for that stream, even between calls. A line is requested only when downstream
asks for another item. The adapter does not create its own background input producer.
Downstream adapters may request subsequent items under their existing bounded buffering rules;
use an explicit read/evaluate loop when every command must finish before the next prompt.
The terminal editing lease is held only for each actual read, not throughout loop bodies.
Closing the stream cancels its active read, waits for terminal restoration, and leaves the
borrowed Editor open. Closing the Editor cancels active input and all its aliases.
Cancellation from alias close is a stream cancellation failure, not a user EOF or Interrupt.

Interactive readers can run as managed pipeline sources. Their native wait services the
existing reactor; it never blocks the interpreter or moves Shelly values to a worker thread.
Independent managed tasks may not write directly to the terminal during an active read;
conflicting editor reads return BusyError, and data/error writes produce a runtime busy
diagnostic. Native background output can later use Reedline's explicit
external printer. Arbitrary child-process writes cannot be intercepted by this API, so
applications must capture them when editing concurrently.

```shy
import std::io
import std::json

# Strings are encoded as JSON strings, one accepted submission per record.
std::json::lines_source $editor.lines | (std::io::write_file "session.jsonl")
```

The byte pipeline stays separate from the terminal channel. Existing pipeline acquisition,
retained-value limits, downstream failure cleanup and marked errors apply. A downstream
failure must cancel/join any active read before its catch runs.

## Native adapter and existing shell

The wrapper uses `std/terminal/init.shy` and `std/terminal/readline/init.shy`; no sibling `terminal.shy`
or `readline.shy` may coexist with those directories. The terminal root exports the short
module binding with a relative public import:

```shy
# std/terminal/init.shy
pub import readline
```

That makes `import std::terminal::{ readline }` bind `readline` locally, so callers use
`readline::Editor`, `readline::History` and `readline::words`. Importing the full module path
alone keeps its full namespace; selecting the exported child provides the short name.
Private Shelly helpers can live beside
the readline root. Rust's reusable adapter belongs under `src/runtime/readline/mod.rs`,
with interpreter binding/callback dispatch under the language interpreter boundary.

The hidden native bridge owns actual Reedline instances. Its opaque handles and operation
IDs are accessible privately to the standard module. Reedline builder calls, Prompt,
Completer, Validator, Highlighter and History traits are adapted directly. Do not implement
a second keyboard loop, text buffer, menu system, undo engine or terminal renderer in Shelly.

Reedline's native callback objects require Send; Shelly closures and their interpreter
references are not Send. A native owner/broker runs Reedline and exchanges bounded owned
snapshot/result messages with the interpreter. Send adapters contain broker identifiers
and channels, not Shelly closures, Rc values or raw interpreter pointers. Shelly executes
callback requests on its own thread while awaiting the read. Use one process-level native
editing owner, with one active read and a bounded registry of idle instances.

On a callback failure the adapter supplies a safe temporary native result, requests Reedline's
existing external break, restores editing state, and hands the original failure back through
the interpreter bridge. Native callback waits must also observe cancellation: an adapter
must not block forever waiting for a callback after the interpreter stops answering.
Enable bounded polling for cancellation using Reedline's existing break signal. Public
Ctrl+C, alias cancellation and internal break have distinct native reasons; do not expose
all of them as the same successful event.

Creation/destruction of native instances is serialized by that owner. Reedline Drop changes
global terminal mode, so dropping an idle instance must never disable raw mode belonging
to another active instance. A closed idle instance may be retired until the active read ends;
retired instances still count against the bounded registry. A native terminal-state guard
restores the prior mode, paste/keyboard protocols and cursor visibility on every exit before
releasing the lease. This guard is required in addition to normal Reedline cleanup. A second
interrupt during script cleanup keeps Shelly's existing abort semantics; native restoration
still runs. SIGKILL cannot offer cleanup guarantees.

The built-in shell keeps its existing Rust editing/evaluation loop. Both frontends reuse
Reedline, native key bindings, history storage, color adaptation and the process-wide terminal
mode gate. Script callbacks use the native owner; the shell retains its Rust providers and
editor on the main thread. It keeps its current prompt evaluation, symbol snapshots,
highlighter, completion adapters, history path,
command timing, startup keystroke handoff and evaluation loop. Opening a custom Editor from
a submitted shell command is valid: the shell's editing lease ended before that command ran.
The custom Editor must not steal or discard queued input, and returning to the shell must
leave the original shell editor/history intact. Migrating the shell REPL itself into Shelly
script or adding source evaluation is outside this wrapper design.

## Limits and delivery

The configurable fields are `max_input_bytes`, `max_completions`, `max_completion_bytes`,
`max_highlight_spans`, `callback_timeout_ms` and `callback_instructions`, all optional Integers
on the immutable Limits configuration. Omitted fields take defaults; invalid values raise
ConfigError. Their ceilings are 1 MiB, 10,000, 4 MiB, 16,384, 100 ms and 250,000 instructions,
respectively; zero is invalid. Prompt and registry limits are fixed in this initial wrapper.

Limits defaults: 64 KiB input snapshots, 1,000 completions with 1 MiB total result bytes,
4,096 highlight spans, 16 KiB prompt text, 50 ms / 100,000 instructions per script callback,
and 32 live or retired editor instances. Configuration has finite validated ceilings.
Byte accounting precedes converting native replies into script values. Oversized initial
input fails before terminal acquisition; an oversized edited buffer aborts the read with
LimitError and restores the terminal before invoking application callbacks.

Input snapshot limits bound the wrapper's messages, returned text and callback work. They
do not claim to bound Reedline's internal paste/undo allocation. A hard native buffer/undo
cap would require an upstream capability and should not be implemented as a replacement
editor. Retained history has its independent budget.

Editor/read/read_event/lines, isolated persistent or memory history, prompt functions,
typed styling, checked callbacks and cancellation are implemented against the same native
adapter. The PTY suite exercises both the script wrapper and the built-in shell's handoff.
Custom arbitrary keymaps, script host-command hooks, remote terminals, password input,
external buffer-editor commands and asynchronous script completion are later extensions.
They are not required for a script to own a useful REPL.

## Hostile review

| Counterexample | Required behavior |
| --- | --- |
| User presses Enter on empty text | Yield `""`; never confuse it with EOF |
| User presses Ctrl+C then submits a command | Cancel the draft once; do not leave a stale runtime interrupt |
| Callback rejects a typo | Keep editing with feedback; no error union or catch required |
| Callback throws a private application error | Restore terminal, propagate concrete error and original frames |
| Editing callback prints, calls HTTP or starts another read | Reject before side effects; no raw-mode deadlock |
| Prompt function is expensive or fails | Evaluate before raw mode; propagate failure without consuming input |
| Native painter repaints a dynamic prompt repeatedly | Reuse a snapshot; no repeated script calls or side effects |
| Completion splits an emoji's UTF-8 encoding | Reject whole result before insertion |
| Cursor moves after results were computed | Apply only matching buffer/cursor revision |
| Highlight callback replaces or duplicates source | Accept checked ranges/styles only; preserve source |
| Two aliases read, or a stream and direct read overlap | BusyError before another byte is consumed |
| Loop breaks or byte-pipeline sink fails during input | Cancel/join active read and restore before catch |
| A second, idle Editor is destroyed during a read | Defer native Drop; keep the active terminal mode intact |
| Another shell submission starts a custom REPL | Separate history/session; reuse terminal only after shell editing ends |
| Stdout is redirected to a file | No prompt or destructor cursor controls enter that file |
| Persistent history becomes corrupt or unavailable | Preserve file and accepted text; default memory fallback warns once |
| Strict history write fails after Enter | Raise HistoryError; accepted text remains recoverable as draft |
| A caller assumes max_input_bytes caps native undo | Document wrapper bound; require native support for a hard engine cap |

Acceptance tests are Shelly scripts using the existing PTY harness. They exercise multiline/paste,
Unicode completion positions, both key modes, callback errors, loop/pipeline cancellation,
restoration after each exit, nested custom REPLs, redirected stdout, separate persistent
histories and real interruption. Existing shell history tests exercise simultaneous writers;
shell highlighting, completion, multiline and startup-input tests cover the shared integration.

## Implementation review and validation

All 4,545 tests passed in the final full acceptance run. Seven focused PTY test files passed,
including the runnable example and a custom REPL inside a built-in shell submission. The
locked offline debug build passed. Clippy completed successfully with 306 warnings, including
large-error warnings in this wrapper. Whitespace, local documentation links, module roots and
the new Rust sources' 100-column limit were checked.

An earlier full run reported one executable-lookup fixture mismatch (`ARGCALL-021`). That
fixture passed immediately in isolation and in the final full run with the executable held
fixed. The cause of the earlier mismatch was not established.

The review corrected three concrete integration failures: loop breaks retaining the borrowed
editor lease, validation seeing a stale buffer when keys arrive in one batch, and cursor-position
queries leaking into redirected stdout. Iteration release now owns an explicit native resource
and propagates through map/filter/typed adapters. Validation uses Reedline's repaint and native
break/resume facilities to obtain its actual buffer and cursor. A terminal I/O guard routes
Crossterm's descriptor-1 controls to the terminal while Shelly writers and child-process setup
retain the original data destination. Both routing and terminal mode restore before script
recovery. The convenience read uses an explicit return escrow through finally.

History storage runs through the existing four-slot owned blocking pool, with retained-text
and on-disk bounds. Strict storage failures preserve pending record IDs for retries. Callback
errors keep concrete identity; native faults record their Rust origin separately from native
dispatch frames. Runtime cancellation has its own native metadata and is not reinterpreted
as the user's Ctrl+C. Native callback waits observe cancellation and inherited operation or
cleanup deadlines. Input and callback-result limits remain distinct from Reedline's internal
undo/paste storage.

Validation here is on macOS. The user's release shell is untouched. Public async completion,
arbitrary key maps, password input and evaluation of entered source remain outside this API.
